================================================================================
0. EXECUTIVE SUMMARY
================================================================================

This review was requested to focus on where the code is inefficient, where bugs hide, and where design
decisions hurt performance. The independent pass concentrated on the three hottest paths in the app:

  1. HUD / chrome state pushes (app/src/browser_window.cpp: pushChromeState / pushChromeTelemetry /
     pushChromeProgress / pushHudState; app/include/explorer/app/chrome_ui.hpp: __updateHud).
  2. Telemetry polling (hal/src/telemetry.cpp; app/src/browser_window.cpp: onTelemetryTick; policy
     src/power_policy.cpp: telemetryIntervalMs).
  3. Download progress handling (engine/src/cef_client.cpp: OnBeforeDownload / OnDownloadUpdated;
     app/src/browser_window.cpp: onTabDownloadUpdated).

CONFIRMED IN THIS PASS — the headline finding:

  [P1] pushHudState() rebuilds the entire HUD payload and re-executes a large JS message on EVERY call,
        with NO change detection, while its sibling pushChromeTelemetry() already implements a signature
        dedup (app/src/browser_window.cpp:724-742, dedup at lines 731-732: "Zero idle JS IPC when nothing
        changed!"). pushHudState() has no equivalent guard. It is invoked from onTelemetryTick() every
        2000ms (5s on battery, HUD closed) whenever hud_visible_ is true (lines 1467-1474), from
        setStatusBanner() (line 664), from toggle flows (lines 916-921), from vault/webapp/login handlers,
        from download updates and from power-source changes.

        Practical impact:
          - With the HUD open, the full HUD JSON is rebuilt every 2s: vault list via listAll() which
            RETURNS THE VECTOR BY VALUE including all credentials (vault/src/password_vault.cpp:308-310),
            downloads array, and the installed-webapp list via listInstalled() which scans and parses
            ~/.local/share/applications and reads every .desktop file (webapp/src/webapp_installer.cpp:177-202).
          - The renderer then clears innerHTML and recreates every HUD DOM node (chrome_ui.hpp:744-832)
            -> focus/scroll loss and GC churn on every tick, even when values are identical.
          - The same full push is repeated for tiny state changes (status banner, cinema toggle) that only
            touch one field.

2. BUG FINDINGS (INDEPENDENT PASS — performance-correlated correctness bugs)
================================================================================

[B1] HUD push has no change detection while the telemetry push does -> inconsistent dedup, redundant work.
  Files: app/src/browser_window.cpp (pushHudState 756-842 vs pushChromeTelemetry 724-742);
         app/src/browser_window.cpp (onTelemetryTick 1461-1479).
  Detail: pushChromeTelemetry() computes last_telemetry_sig_ and returns early when unchanged (line 731-732).
  pushHudState() unconditionally builds the full message and calls ExecuteJavaScript on every invocation.
  onTelemetryTick() therefore executes a full HUD JS push every tick while the smaller telemetry widget push is
  correctly skipped when idle. The asymmetry means the biggest UI cost path is exactly the one lacking the guard.
  Impact: unnecessary renderer work / GC / DOM rebuild every 2s with HUD open; wasted CPU even when telemetry is
  static (e.g. parked machine).
  Rec: Mirror the last_telemetry_sig_ pattern in pushHudState (per-field sigs or a single snapshot sig); skip
       ExecuteJavaScript when the snapshot is unchanged.

[B2] setStatusBanner() fans out into a FULL HUD push.
  Files: app/src/browser_window.cpp (662-665), (756-842).
  Detail: A one-line status message change re-runs the entire HUD builder, including the vault list copy and the
  installed-webapp filesystem scan, then rebuilds all HUD DOM nodes.
  Impact: tiny state change -> expensive update; multiplies cost of banner-driven updates.
  Rec: Push only the statusMsg field (targeted update) or reuse a diffed HUD state object.

[B3] Download progress events trigger FULL chrome + FULL HUD pushes, with no progress-specific coalescing.
  Files: engine/src/cef_client.cpp (OnDownloadUpdated 301-329; OnBeforeDownload 290-299);
         app/src/browser_window.cpp (onTabDownloadUpdated 1218-1234).
  Detail: Every CEF download progress callback -> observer_->onTabDownloadUpdated(rec) -> pushChromeState()
  (full tabs/vault/battery JSON + ExecuteJavaScript, browser_window.cpp:667-722) AND, when the HUD is open,
  pushHudState(last_snap_) (full HUD rebuild incl. webapp fs scan, :756-842).
  Note that pushChromeProgress() (browser_window.cpp:744-754) ALREADY coalesces progress pushes for tab loading
  (|progress - last_pushed_progress_| < 0.05 and 0.05 < progress < 0.99), proving the coalescing intent exists —
  but the download path bypasses it and re-pushes full state.
  Impact: Large downloads can fire many progress updates per second -> UI-thread + renderer JS churn, lost HUD
  focus, compounding [M2].
  Rec: Push only download id + percent for progress updates; coalesce on meaningful delta (>=1% or ~4Hz).

[B4] Normal shutdown performs TWO session flushes.
  Files: app/src/browser_window.cpp (handleCanClose ~399-418 calls flushSessionNow at 403;
         handleWindowDestroyed ~381-384 calls flushSessionNow; flushSessionNow ~1494-1503).
  Detail: handleCanClose() flushes the session, then CEF closes tabs (erasing them from tabs_) and
  handleWindowDestroyed() flushes again — the second flush can serialize an already-erased tab list
  (see H3/H4 in prior reviews). Write amplification doubles on every clean shutdown.
  Impact: Redundant disk write per shutdown; correctness risk already documented in prior reviews.

3. MEDIUM-SEVERITY FINDINGS / INEFFICIENCIES (INDEPENDENT PASS)
================================================================================

[M1] pushHudState(): full rebuild, no diff, no per-field skip. (See [P1] above — highest-impact perf item.)
[M2] onTabDownloadUpdated(): unconditional full pushChromeState() + pushHudState() per progress event (B3).
[M3] Telemetry full sweep + /proc/stat open/read/close on the UI thread every tick (hal/src/telemetry.cpp:
     sample() 91-138, sampleLite() 140-163, sampleCpuPercent() 198-222; tick at app/src/browser_window.cpp
     1465-1468). sample() reads ~12 sysfs/power files; full sample only needed when HUD is open, lite when closed.
[M4] Telemetry reschedule is unconditional and interval is fixed (policy/src/power_policy.cpp:45-47:
     hud_open ? 2000ms : (battery ? 5000ms : 2000ms)); no skip-when-idle and no adaptive polling. Combined
     with [M1], the idle case still rebuilds state it does not need.
[M5] findTab(): O(n) linear scan (app/src/browser_window.cpp:1509-1514) reached via activeTabEntry() from
     pushChromeState(), pushHudState() (via activeTabEntry for origin/title) and every tab handler
     (onTabAddressChanged 1130, onTabTitleChanged 1144, onTabFaviconChanged 1158, onTabProgressChanged 1167,
     onTabLoadingChanged 1175, onTabScrollRevealTopBar 1236, onTabLoginSubmitted 1247). With many tabs, each
     event costs O(n).
[M6] pushChromeState(): full JSON rebuild on every event (667-722) — including battery pill, tabs array, vault
     site-creds lookup via findForOrigin (681-683, vault linear scan at password_vault.cpp:299-306) and
     ExecuteJavaScript. Fires on title/loading/address changes, toggles, power sync, close paths.
[M7] vault listAll(): returns the whole entries_ vector by value on every HUD push (308-310); HUD only consumes
     origin + username. Copy includes password data movement per push.
[M8] webapp listInstalled(): directory iteration + per-file ifstream parse + sort, on the UI thread, on every
     HUD push (webapp_installer.cpp:177-202, called at browser_window.cpp:832). Confirmed by inspection; prior
     reviews called it [P11].

5. PERFORMANCE ANALYSIS AND WHERE TO IMPROVE PERFORMANCE
================================================================================

Ranked improvement areas (highest expected win first):

[P1] HUD state push without change detection — BIGGEST UI/perf win.
    Files: app/src/browser_window.cpp:756-842; chrome_ui.hpp:715-833; invoked from 1467-1474, 629, 664, 916-921,
           942-945, 1008, 1096, 1232-1233, 1254-1255, 1433-1434.
    Current: full rebuild + full DOM rebuild (innerHTML='') every push, no dedup.
    Fix: add per-push signature/dedup (mirror pushChromeTelemetry's last_telemetry_sig_) and/or targeted field
         updates; skip ExecuteJavaScript when unchanged.

[P2] Download progress → full state pushes — second biggest win.
    Files: engine/src/cef_client.cpp:301-329; app/src/browser_window.cpp:1218-1234; pushChromeProgress coalesce
           exists at browser_window.cpp:744-749 but is bypassed.
    Fix: progress-only message (id/percent) with coalescing (>=1% delta or 4Hz); stop pushing full chrome/HUD state.

[P3] Telemetry sampling on UI thread + oversized lite sample.
    Files: hal/src/telemetry.cpp:45-222; app/src/browser_window.cpp:1465-1468.
    Fix: background sampler thread posting snapshots; cache sysfs fds; trim sampleLite() to AC + battery status.

[P4] Tab lookup O(n) — add hash index (browser_window.cpp:1505-1514 + ~10 handler call sites).

[P5] vault listAll() by-value copy per HUD push (vault/src/password_vault.cpp:308-310) — expose const-ref or
      origin+username-only accessor.

[P6] webapp listInstalled() fs scan per HUD push on UI thread (webapp/src/webapp_installer.cpp:177-202) — cache
      with invalidation on install/uninstall.

[P7] pushChromeState() full rebuild per event incl. vault linear scan (browser_window.cpp:667-722, vault
      findForOrigin 299-306) — diff-based push for high-frequency fields (progress/loading) vs low-frequency
      (tabs list, title).

[P8] resolveDownloadPath linear collision scan (engine/src/cef_client.cpp:58-67) — unique suffix instead of 999
      stats.

[P9] Session save write amplification (browser_window.cpp:381-384, 399-403, 1494-1503) — single flush path.

================================================================================
6. KEY DESIGN ISSUES
================================================================================

[D1] No unified diff-based state push model.
    Three push helpers exist with different semantics (full pushChromeState, deduped pushChromeTelemetry,
    coalesced pushChromeProgress, non-deduped pushHudState). Design intent (dedup/coalesce) is scattered across
    four functions; no single "StateDiff -> message" abstraction. This is the root cause of [P1]-[P3] overhead.

[D2] Imperative polling + UI-thread I/O.
    Telemetry tick does sysfs reads on the UI thread and unconditionally reschedules; HUD state pushed through
    giant inline JS strings. A snapshot cache + background sampler + targeted renderer messages would remove the
    whole class of UI-thread stalls.

[D3] Full-state JS pushes for UI.
    pushHudState sends a single large object with all lists every time; renderer clears innerHTML. A structured,
    diff-style message protocol + node reuse would cut IPC and GC cost.

[D4] (carried) Async lifetime ownership not modeled — detached threads / raw this (prior H1, re-confirmed).

[D5] (carried) Hardware assumptions baked in — not a perf defect per se, noted for context.

================================================================================
7. RECOMMENDED PRIORITY ORDER (performance-first)
================================================================================

1. Add change detection to pushHudState() and skip no-op pushes (P1) — immediately removes the every-2s full
   rebuild + DOM rebuild while values unchanged; lowest effort, highest win. Also route setStatusBanner through
   targeted update (B2).
2. Replace download-path full pushes with progress-only coalesced pushes (P2/B3).
3. Move telemetry sampling off the UI thread and trim/refresh sampleLite scope (P3/M3); add idle skip (P4/M4).
4. Add O(1) tab lookup index (P4/M5).
5. Change vault listAll() to const-ref / lean accessor (P5/M7).
6. Cache installed-webapp list with invalidation (P6/M8).
7. Diff pushChromeState high/low frequency fields (P7/M6).
8. Unique download path suffix; single session flush (P8/L1, B4/L2).
