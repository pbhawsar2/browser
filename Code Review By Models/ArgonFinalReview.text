[ARGON-H1] Normal Window Shutdown Overwrites `session.json` With Empty Tabs
--------------------------------------------------------------------------------
- Severity: CRITICAL (100% reproducible session data loss on normal close)
- Location:
  * `app/src/browser_window.cpp:381-385` (`handleWindowDestroyed`)
  * `app/src/browser_window.cpp:399-436` (`handleCanClose`)
  * `app/src/browser_window.cpp:1388-1416` (`onTabClosed`)
  * `app/src/browser_window.cpp:1494-1503` (`flushSessionNow`)
- Root Cause:
  1. When the user closes the window, `handleCanClose()` sets `closing_ = true`, calls
     `flushSessionNow()` (which saves the active tabs to `session.json`), and then calls
     `TryCloseBrowser()` on all tabs.
  2. As each tab closes, `ExplorerCefClient::OnBeforeClose` invokes `onTabClosed(tab_id)`,
     which erases the tab from `tabs_` (`tabs_.erase(it)` at line 1405).
  3. Once `tabs_` and `retiring_tabs_` are empty, `checkFinishShutdown()` closes the
     `CefWindow`, firing `handleWindowDestroyed()`.
  4. `handleWindowDestroyed()` unconditionally calls `flushSessionNow()` a second time
     (line 384). Because `tabs_` is now empty, it overwrites `session.json` with
     `"tabs": []`.
- How to Fix:
  1. Add a boolean member `bool session_flushed_on_close_ = false;` to `BrowserWindow`.
  2. In `handleCanClose()`, before initiating tab teardown, if `!session_flushed_on_close_`,
     call `flushSessionNow()` and set `session_flushed_on_close_ = true;` and
     `session_dirty_ = false;`.
  3. In `flushSessionNow()` and `scheduleSessionSave()`, return immediately if
     `session_flushed_on_close_` is `true`.
  4. Remove the redundant `flushSessionNow()` call from `handleWindowDestroyed()` (or guard
     it with `if (!session_flushed_on_close_) flushSessionNow();`).

[ARGON-H2] Close State Machine Destroys Chrome Prematurely & Breaks on Cancel
--------------------------------------------------------------------------------
- Severity: HIGH (Broken chromeless window if page `beforeunload` cancels close; iterator
  invalidation risk)
- Location:
  * `app/src/browser_window.cpp:399-436` (`handleCanClose`)
  * `app/src/browser_window.cpp:520-523` (`closeTab`)
  * `app/src/browser_window.cpp:1344-1386` (`onTabDoClose`)
- Root Cause:
  1. `handleCanClose()` destroys `hud_overlay_`, `hud_view_`, and `chrome_view_` on the
     very first close attempt BEFORE calling `TryCloseBrowser()` on content tabs.
  2. In CEF, `TryCloseBrowser()` returns `false` on its first invocation while the renderer
     evaluates `beforeunload` handlers (and also returns `false` if the user chooses "Stay
     on Page").
  3. If the user cancels unload, `closing_` remains `true`, `chrome_view_` and `hud_view_`
     are already destroyed (leaving a permanently chromeless window), and `closeTab()`
     returns early at line 522 (`if (closing_) return;`).
  4. Furthermore, `handleCanClose()` iterates directly over `tabs_` and `retiring_tabs_`
     while calling `TryCloseBrowser()`. If `OnBeforeClose` fires synchronously for any tab,
     `onTabClosed()` mutates `tabs_` / `retiring_tabs_` mid-loop (iterator invalidation UB).
- How to Fix:
  1. Snapshot the `CefRefPtr<CefBrowser>` handles from `tabs_` and `retiring_tabs_` into a
     local `std::vector<CefRefPtr<CefBrowser>>` before calling `TryCloseBrowser()`.
  2. Do NOT destroy `hud_overlay_`, `hud_view_`, or `chrome_view_` inside `handleCanClose()`
     while content tabs are still open. Only tear down `hud_overlay_`/`hud_view_`/`chrome_view_`
     once `all_ready` is `true` (or inside `handleWindowDestroyed()`).
  3. If `handleCanClose()` is cancelled or a tab remains alive after unload prompt
     cancellation, allow normal tab operations by distinguishing window-close teardown from
     individual tab close.

[ARGON-H3] Use-After-Free & Dangling `this` in Detached Threads and Posted Tasks
--------------------------------------------------------------------------------
- Severity: HIGH (Undefined Behavior / crash on shutdown during filter update, WebApp
  install, or D-Bus watcher callbacks)
- Location:
  * `shield/src/content_shield.cpp:117-122, 164-225` (`BraveAdblockShield::updateFilterListsAsync`)
  * `app/src/browser_window.cpp:224-234, 357-378, 899-904, 1016-1022, 1351, 1379, 1461-1479, 1484`
  * `hal/src/power_governor.cpp:150-187` (`LinuxPowerGovernor::setPerformanceHoldAsync`)
  * `hal/src/display_refresh.cpp:251-260` (`MutterDisplayRefreshCtrl::setEdpRefreshRateAsync`)
- Root Cause:
  1. `BraveAdblockShield::updateFilterListsAsync()` spawns a detached thread capturing raw
     `this`. It runs up to three `curl` commands (up to 20s each = 60s) and then accesses
     `this->filters_dir_`, `this->handle_`, and `explorer_brave_shield_reload(handle_, ...)`.
     If the user quits the browser while an update is in progress, `~BraveAdblockShield()`
     calls `explorer_brave_shield_free(handle_)`, causing a Use-After-Free in Rust/C++.
     Also, two concurrent clicks on "Update EasyList & Privacy Filters" race on the same
     `*.tmp` files in `filters_dir_`.
  2. `BrowserWindow` posts delayed and cross-thread tasks using `base::Unretained(this)`.
     Checking `if (alive_.load())` on a background thread before calling `CefPostTask` still
     races `~BrowserWindow()` between the `CefPostTask` call and UI-thread execution.
  3. `~BrowserWindow()` does not call `services_.power_gov->shutdown()` or
     `services_.display_ctrl->shutdown()` (only `handleWindowDestroyed()` does).
- How to Fix:
  1. In `BrowserWindow`, add `std::shared_ptr<std::atomic<bool>> life_token_ = std::make_shared<std::atomic<bool>>(true);`
     (set `*life_token_ = false` in `handleWindowDestroyed()` and `~BrowserWindow()`).
     Wrap all `CefPostTask` / `CefPostDelayedTask` callbacks in a small helper lambda or
     `CefTask` that captures `life_token_` by value and only dereferences `BrowserWindow*`
     on `TID_UI` if `life_token_->load()` is true.
  2. Call `power_gov->shutdown()` and `display_ctrl->shutdown()` in `~BrowserWindow()` as
     well as `handleWindowDestroyed()` (both `shutdown()` methods are already idempotent).
  3. In `BraveAdblockShield`:
     - Add `std::atomic<bool> updating_{false};` to reject overlapping update requests.
     - Store the worker in a member `std::thread update_thread_;` (or share ownership of the
       Rust handle via `std::shared_ptr`), and join `update_thread_` in
       `~BraveAdblockShield()` so the background thread can never outlive `handle_`.

[ARGON-H4] Non-Async-Signal-Safe `fork()` in Multithreaded CEF Process & Zombie Leaks
--------------------------------------------------------------------------------
- Severity: HIGH (Potential child deadlock on `malloc` lock + zombie `<defunct>` process
  accumulation)
- Location:
  * `app/src/browser_window.cpp:97-105` (`spawnDetachedXdgOpen`)
  * `webapp/src/webapp_installer.cpp:63-86` (`runProcessNoShell`)
  * `webapp/src/webapp_installer.cpp:213-223` (`LinuxWebAppInstaller::launch`)
  * `shield/src/content_shield.cpp:192-209` (`updateFilterListsAsync`)
- Root Cause:
  1. CEF runs dozens of threads. After `fork()` in a multithreaded process, POSIX permits
     only async-signal-safe functions before `exec*`.
  2. `runProcessNoShell()` allocates a `std::vector<char*>` on the heap in the child after
     `fork()` and calls `execvp()`.
  3. `LinuxWebAppInstaller::launch()` allocates two `std::string` objects (`app_arg`,
     `id_arg`) on the heap in the child after `fork()` and never calls `waitpid()`, leaving
     a zombie process every time a WebApp is launched and exits.
  4. `spawnDetachedXdgOpen()` calls `fork()` + `execlp()` without `waitpid()`, leaving a
     zombie `<defunct>` process every time the user clicks "Open File" or "Open Downloads
     Folder".
- How to Fix:
  1. Replace `fork()` + `exec*` in `runProcessNoShell` and `updateFilterListsAsync` with
     `posix_spawnp()` (using `posix_spawn_file_actions_addopen` / `adddup2` to redirect
     `stdout`/`stderr` to `/dev/null`) followed by `waitpid()`.
  2. For fire-and-forget launches (`spawnDetachedXdgOpen` and `LinuxWebAppInstaller::launch`),
     either use the classic POSIX double-fork idiom (where the parent `waitpid()`s the
     first child immediately, and the grandchild `setsid()`s and `execv`/`posix_spawnp`s
     with pre-built `const char* argv[]` constructed BEFORE `fork()`), OR spawn via
     `posix_spawnp` and reap asynchronously on a background waiter thread.

[ARGON-H5] Release Unit Tests Compile Out `assert()` (`-DNDEBUG`) & Vault Accepts `javascript:` / `data:` Origins
--------------------------------------------------------------------------------
- Severity: HIGH (Broken security validation in `AesGcmPasswordVault::normalizeOrigin`
  masked by vacuous Release tests)
- Location:
  * `vault/src/password_vault.cpp:113-137` (`AesGcmPasswordVault::normalizeOrigin`)
  * `vault/tests/test_vault.cpp:24`
  * `CMakeLists.txt:6-8, 26, 89-114`
  * `hal/tests/test_hal.cpp`, `policy/tests/test_policy.cpp`, `shield/tests/test_shield.cpp`,
    `vault/tests/test_vault.cpp`, `webapp/tests/test_webapp.cpp`
- Root Cause:
  1. `AesGcmPasswordVault::normalizeOrigin` checks `auto scheme_pos = s.find("://");` and if
     `"://"` is not found, it blindly defaults `scheme = "https"` and `host_start = 0`.
  2. Consequently, `"javascript:alert(1)"` is normalized to `"https://javascript:alert(1)"`
     and `"data:text/html,hi"` is normalized to `"https://data:text"`, instead of being
     rejected (`""`).
  3. `test_vault.cpp:24` has `assert(!v.saveOrUpdate("javascript:alert(1)", "u", "p"));`.
     In Debug builds this assertion fails and aborts.
  4. Because `CMakeLists.txt` defaults `CMAKE_BUILD_TYPE` to `Release` (which passes
     `-DNDEBUG`), all `assert(...)` statements — including the function calls inside them —
     are completely stripped from `test_hal`, `test_policy`, `test_shield`, `test_vault`,
     and `test_webapp`!
- How to Fix:
  1. In `AesGcmPasswordVault::normalizeOrigin(const std::string& raw_url)`:
     - Before defaulting to `"https"`, check if there is a colon `:` before the first `/`,
       `?`, or `#` when `"://"` is absent:
       * If a colon exists (e.g. `javascript:alert(1)`, `data:...`, `mailto:...`,
         `about:blank`, `chrome:...`), verify whether the substring after `:` is purely a
         valid numeric port `1..65535` preceded by a valid hostname (e.g. `localhost:3000`
         or `example.com:8443`).
       * Specifically, if the prefix before `:` is a known non-http scheme (`javascript`,
         `data`, `mailto`, `file`, `about`, `chrome`, `explorer`, `blob`, `ws`, `wss`, `ftp`)
         or if the characters after `:` up to `/ ? #` are not all digits (`0-9`), return
         `""` immediately!
     - Also reject authorities containing spaces, control characters, backslashes, or
       invalid port numbers, and strip default ports (`:443` for `https`, `:80` for `http`).
  2. In `test_hal.cpp`, `test_policy.cpp`, `test_shield.cpp`, `test_vault.cpp`, and
     `test_webapp.cpp`:
     - Replace `<cassert>` / `assert(...)` with an always-active `EXP_CHECK(cond)` macro
       (matching `CHECK(cond)` in `app/tests/test_app_stores.cpp:9-15`) that evaluates
       `cond` unconditionally in both Release and Debug builds and exits with code 1 on
       failure.

[ARGON-H6] PPD Performance-Hold Race & refresh-rate Worker Desynchronization
--------------------------------------------------------------------------------
- Severity: HIGH (Leaked PPD performance holds pinning CPU in high-power mode; out-of-order
  refresh rate transitions)
- Location:
  * `hal/src/power_governor.cpp:150-187, 249-272` (`LinuxPowerGovernor::setPerformanceHoldAsync`)
  * `hal/src/display_refresh.cpp:251-264` (`MutterDisplayRefreshCtrl::setEdpRefreshRateAsync`)
- Root Cause:
  1. In `LinuxPowerGovernor::setPerformanceHoldAsync(bool hold)`:
     - `ppd_cookie_` is only populated AFTER the asynchronous D-Bus call
       `holdPpdProfileSync()` returns on a detached thread.
     - If `setPerformanceHoldAsync(true)` is called twice before the first D-Bus call
       returns (e.g., startup `syncSystemPower` at 150ms + UPower/telemetry sync), both
       calls see `!ppd_cookie_.has_value()`, spawning two threads that each acquire a PPD
       hold. The second thread overwrites `ppd_cookie_`, leaking the first cookie forever
       (the CPU remains locked in `performance` profile even on battery!).
     - Moreover, the detached lambda captures `this` without synchronization against
       object destruction.
  2. In `MutterDisplayRefreshCtrl::setEdpRefreshRateAsync(double target_hz)`:
     - `last_hz_.exchange(rounded)` updates `last_hz_` before the async D-Bus call runs, and
       rapid changes spawn concurrent detached threads that can finish out of order.
- How to Fix:
  1. In `LinuxPowerGovernor`:
     - Add `bool ppd_in_flight_ = false;` protected by `mu_`, and a `std::condition_variable cv_;`
       (or track the single worker thread).
     - When `setPerformanceHoldAsync(hold)` is called, update `ppd_desired_ = hold;`. If
       `ppd_in_flight_` is already `true`, return immediately — let the in-flight worker loop
       until the actual state (`ppd_cookie_.has_value()`) matches `ppd_desired_` or
       `stop_watcher_` is set!
     - In `shutdown()`, wait for `ppd_in_flight_` to become `false` under `cv_` before
       releasing any remaining `ppd_cookie_`. This guarantees zero leaked cookies, zero
       out-of-order D-Bus calls, and zero Use-After-Free on `this`.
  2. In `MutterDisplayRefreshCtrl`:
     - Apply the same single-in-flight state-reconciliation pattern (store
       `desired_hz_`, let one worker reconcile `applied_hz_` -> `desired_hz_`, and wait for
       completion in `shutdown()`).

- Location:

  * `app/src/browser_window.cpp:882-889` (`onChromeCommand("open_panel")`)
  * `app/include/explorer/app/chrome_ui.hpp:333-337, 693-699`
- Root Cause:
  - In `chrome_ui.hpp:333-337`, every top-bezel button passes a tab name argument:

    } else if (cmd == "open_panel") {
