DeepSeak Review — Explorer Browser
Date: 2026-11-21
Scope: Independent full-source review of hal/, policy/, shield/, shield-brave/, vault/, webapp/, engine/, app/, tests, CMake, installer/updater scripts, and README.
Method: Read the non-generated sources and build files; built the Rust static library; built and ran the Release test suite; independently configured a Debug build at /tmp/opencode/review-debug and ran CTest there; inspected CEF callbacks, object lifetimes, persistence paths, and the security trust boundaries.
Status of tree: No source files were modified by this review. `git status` showed only the pre-existing untracked BeamCodeReview.text. This review is independent of that document; several of its claims were checked and some are corrected below.

================================================================================
0. EXECUTIVE SUMMARY
================================================================================

The modular separation is generally good: HAL, policy, shield, vault, webapp, engine, and app are cleanly separated, and the shield/vault implementations are small enough to audit. The largest problems are not in the module boundaries; they are in lifecycle ownership, the test strategy, shutdown/session state, and a few security-sensitive validation paths.

The most important conclusions:

1. The Release test suite is largely vacuous. Release builds use -DNDEBUG, five of six test suites use assert(), and every call inside an assert is removed. The suite still reports 6/6 passing. A Debug build exposes a real failure in test_vault (javascript: origin accepted), proving the Release green result is not evidence of correctness.
2. Normal window shutdown can overwrite a good session with an empty one. The close path saves the session, tabs are then erased as CEF closes them, and handleWindowDestroyed saves again from the now-empty tab list.
3. The close state machine destroys the chrome/HUD before tab close confirmation and leaves `closing_` set if a page cancels unload. A cancelled close can leave a chromeless, partially stuck window.
4. Detached threads and posted tasks capture raw `this` pointers and can outlive BrowserWindow or BraveAdblockShield. The filter updater can run for up to 60 seconds (three curl calls) after the user quits.
5. Several fork/exec sites perform non-async-signal-safe work in the child of a multithreaded CEF process (malloc, std::string, std::vector, execlp/execvp). This can deadlock the child before exec.
6. Downloads are accepted automatically with no user confirmation, and the engine-builder disables Safe Browsing. A page can cause files to be written to ~/Downloads; the HUD can then open them with xdg-open.
7. Origin validation in the vault accepts scheme-like strings that do not contain "://" (javascript:, data:, mailto:). The Debug test fails on `javascript:alert(1)`.
8. The local CEF installer reuses a world-writable /tmp directory if present and neither installer nor updater verifies a checksum/signature. This is a local supply-chain risk.
9. Widevine is not actually registered with CEF. Adding an `enable-widevine` command-line switch is not sufficient; CefRegisterWidevineCdm is absent.
10. The PPD performance-hold code can acquire duplicate holds because `ppd_cookie_` remains empty until the asynchronous acquire completes.

Severity key: HIGH = security/data-loss/stability issue that should be fixed before calling the browser production-ready; MEDIUM = functional, privacy, performance, or portability defect with a realistic user impact; LOW = hardening, cleanup, or documentation issue.

[H1] Release tests are compiled with assertions removed; the green CTest result is misleading
Files: CMakeLists.txt:6-8,26,89-113; hal/tests/test_hal.cpp; policy/tests/test_policy.cpp;
       shield/tests/test_shield.cpp; vault/tests/test_vault.cpp; webapp/tests/test_webapp.cpp
Evidence:
- CMake defaults to Release and uses `-O3`; CMake's Release configuration adds `-DNDEBUG`.
- Five of the six test executables use plain `assert()`. Only app/tests/test_app_stores.cpp defines a custom `CHECK`.
- With NDEBUG, the assert expressions are not evaluated. That removes not just the checks but the calls:
  * test_vault never calls saveOrUpdate/remove/findForOrigin inside asserts.
  * test_shield never calls evaluate() for its block/allow cases.
  * test_webapp never calls uninstall() for its traversal cases.
  * test_hal never applies or verifies throttling.
  * test_policy never exercises most policy assertions.
- The test binaries still print "ALL PASSED" and return 0, so install.sh's ctest step gives false confidence.
- The Debug run proves the suite is not actually green: test_vault fails at line 24.
Impact: regressions in the most security-sensitive code (vault origin handling, shield decisions, webapp path validation) can ship while CI says everything passed.
Recommendation:
- Build tests in Debug (or at least without NDEBUG) in CI and in install.sh.
- Replace assert() with an always-on test macro/check framework in all suites.
- Never put side-effecting calls inside an assertion.
- Add a CTest label/configuration for Debug and run both Debug and Release.
- Consider `-DNDEBUG` only for the browser target, not for test targets.

[H2] Vault origin validation accepts non-URL schemes and fails its own test
File: vault/src/password_vault.cpp:113-137; vault/tests/test_vault.cpp:22-26
Evidence:
- `normalizeOrigin` defaults the scheme to "https" whenever the input does not contain "://".
- `javascript:alert(1)` therefore becomes `https://javascript:alert(1)`, and saveOrUpdate succeeds.
- `data:text/html,...` becomes `https://data:text`, and `mailto:user@example.com` becomes a bogus https authority (the '@' check then rejects mailto, but data: without '@' is accepted).
- The comment says non-web schemes are rejected, but the implementation only rejects them when they contain "://".
- The Debug test fails exactly on the javascript case. The Release test hides it because the assert is removed.
Impact:
- The vault's origin key is not guaranteed to be a real web origin.
- A future caller that trusts `normalizeOrigin` (for example autofill or a credential UI) can be confused by invalid origins.
- The test suite's own security contract is violated.
Recommendation:
- Use a real URL parser (CEF's GURL, or a small strict parser) and require a valid http/https scheme and non-empty host.
- Reject any input whose scheme is not exactly http or https, even when "://" is absent.
- Canonicalize host (lowercase, IDNA/punycode), drop default ports, reject userinfo, invalid ports, and control characters.
- Add tests for javascript:, data:, mailto:, file:, chrome:, `https://`, invalid ports, Unicode hosts, and default-port duplicates.

[H3] Normal shutdown can overwrite the saved session with an empty tab list
Files: app/src/browser_window.cpp:381-384,399-436,1388-1416,1494-1506
Evidence:
- `handleCanClose()` sets `closing_ = true`, calls `flushSessionNow()` (line 403), then calls `TryCloseBrowser()` on every tab.
- As CEF closes each tab, `ExplorerCefClient::OnBeforeClose` calls `onTabClosed()`, which erases the tab from `tabs_` (lines 1400-1406).
- `handleWindowDestroyed()` unconditionally calls `flushSessionNow()` again (line 384).
- `flushSessionNow()` serializes the current `tabs_`; if the tabs have already been erased, it writes an empty URL list.
- The last-tab path is especially exposed: `closeTab()` calls `window_->Close()` without removing the tab, then the same sequence runs.
Impact: Session restore silently loses the user's tabs on a normal exit. The saved state depends on CEF's internal close ordering, so it may be intermittent and hard to reproduce.
Recommendation:
- Save the session once, at the start of close, and do not save again from `handleWindowDestroyed` (or guard the second save with `if (!closing_)`).
- Better: snapshot the session data into a local struct in `handleCanClose` and write that snapshot, independent of tab teardown.
- Add an integration test that closes a window with N tabs and verifies session.json still has N URLs.

[H4] Close state machine can leave a chromeless, stuck window and is re-entrant
Files: app/src/browser_window.cpp:399-436,520-563,1346-1386
Evidence:
- `handleCanClose()` destroys the HUD overlay and chrome view before it knows whether all tabs will close (lines 405-417).
- If a tab's beforeunload handler cancels, `TryCloseBrowser()` returns false, `handleCanClose()` returns false, but `closing_` is never reset.
- Once `closing_` is true:
  * `closeTab()` returns immediately (line 522), so the user cannot close the remaining tabs normally.
  * `onTabDoClose()` returns false for every tab (line 1348), which sends CEF's standard close notification back to the same top-level window.
- `handleCanClose()` iterates `tabs_` and `retiring_tabs_` while calling `TryCloseBrowser()`; if CEF delivers `OnBeforeClose` synchronously, `onTabClosed()` can erase the current element and invalidate the iteration.
- The result can be a window with no chrome/HUD, tabs that cannot be closed through the normal path, or a shutdown that depends on an OnBeforeClose callback that never arrives.
Impact: A page can cancel the window close and leave the browser in a broken UI state. This is a realistic user flow (a site with an unload confirmation).
Recommendation:
- Do not destroy chrome/HUD until every tab has confirmed close.
- Reset `closing_` when the close is cancelled.
- Do not return false from `onTabDoClose()` merely because `closing_` is set; distinguish "window close in progress" from "tab close in progress".
- Copy the tab IDs to close into a local vector before calling TryCloseBrowser, so callback-driven erasure cannot invalidate iteration.
- Add a timeout/fallback for OnBeforeClose and a test with a beforeunload handler.

[H5] Detached threads and posted tasks capture raw `this` and can outlive their owners
Files:
- shield/src/content_shield.cpp:117-122,164-224
- app/src/browser_window.cpp:226-234,381-384,899-906,1014-1023,1458-1474
- hal/src/power_governor.cpp:150-186,189-246,249-272
- hal/src/display_refresh.cpp:251-260
Evidence:
- `BraveAdblockShield::updateFilterListsAsync()` starts `std::thread([this, ...]{ ... }).detach()`.
  The thread reads `filters_dir_`, calls `loadCombinedRules()`, calls `ruleCount()`/`handle_`, and invokes the completion callback. The destructor frees `handle_`. Three curl downloads can run for up to 20 seconds each, so quitting during an update leaves the thread using freed state.
- The completion callback captures `BrowserWindow* this` and checks `alive_` before posting an `Unretained(this)` task. There is a race between the check and task execution.
- `webapp_install` starts a detached thread that captures `this`, then posts `onWebAppInstallFinished` with `Unretained(this)` after checking `alive_`. The same race exists.
- `LinuxPowerGovernor::setPerformanceHoldAsync()` starts detached acquire/release threads; `shutdown()` joins only the watcher, not these workers.
- `MutterDisplayRefreshCtrl::setEdpRefreshRateAsync()` starts detached threads; the lambda itself captures only `target_hz`, so it is not a UAF, but multiple threads can apply modes out of order.
- `BrowserWindow::~BrowserWindow()` detaches clients but does not call `power_gov->shutdown()` or `display_ctrl->shutdown()`; those are only called from `handleWindowDestroyed()`. If the object is destroyed through another path, the watcher callbacks still capture a dead `this`.
- The constructor posts `syncSystemPower` and `onTelemetryTick` with `Unretained(this)`; those tasks can outlive the window.
Impact: Use-after-free/crash on quit, especially during a filter update or webapp install; possible shutdown hang or corrupted state. This is undefined behavior, not just a leak.
Recommendation:
- Introduce a refcounted lifetime token (shared_ptr<Lifetime>) captured by every async task; check it on the UI thread before touching BrowserWindow.
- Own all workers in a small executor/thread pool; provide `cancel()`/`shutdown()` and join.
- Do not detach threads that touch object state.
- Make `shutdown()` idempotent and call it from the destructor as well as the window-destroyed path.
- Use `CefPostTask` with a refcounted helper rather than `base::Unretained(this)`.

[H6] fork() followed by non-async-signal-safe child code in a multithreaded process
Files:
- webapp/src/webapp_installer.cpp:63-86,213-223
- shield/src/content_shield.cpp:192-209
- app/src/browser_window.cpp:96-105
Evidence:
- CEF runs many threads. After fork(), POSIX only guarantees async-signal-safe functions in the child before exec.
- `runProcessNoShell()` builds `std::vector<char*>` in the child (heap allocation), then calls `execvp()` (PATH search and possibly allocation).
- `launch()` builds `std::string app_arg` and `std::string id_arg` in the child (heap allocation), then calls `execl()`.
- `content_shield.cpp` and `spawnDetachedXdgOpen()` call `execlp()` in the child (not async-signal-safe).
- If another thread holds the malloc/stdio lock at the moment of fork, the child can deadlock before exec.
Impact: Intermittent hangs when installing a webapp, updating filters, or opening a downloaded file. The parent may wait forever in `waitpid()`.
Recommendation:
- Use `posix_spawn()` (or `posix_spawnp()`) for all helper processes.
- If fork must be used, pre-build argv/envp before fork and use `execv()`/`execve()` with absolute paths; use only async-signal-safe calls in the child.
- Reap children (or double-fork) and handle SIGCHLD.

[H7] Downloads are auto-accepted with no user confirmation; Safe Browsing is disabled
Files:
- engine/src/cef_client.cpp:290-299
- engine-builder/args.gn:17-22
- app/src/browser_window.cpp:992-1000
Evidence:
- `OnBeforeDownload()` immediately calls `callback->Continue(dest.string(), false)` for every download. There is no prompt, no content-type/size check, and no user gesture requirement.
- The custom engine build sets `safe_browsing_mode = 0`, so Chromium's download protection is not available.
- `dl_open` opens any completed download path with `xdg-open`; an executable or `.desktop` file can be launched with one click from the HUD.
Impact:
- A page can write files to the user's Downloads directory without an explicit save dialog (drive-by download).
- The user may be social-engineered into opening an executable.
- This is a meaningful security regression compared with mainstream browsers.
Recommendation:
- Ask the user before starting a download; show source URL, filename, size, and type.
- Reject or warn on executable/MIME types; do not auto-open them.
- Enable Safe Browsing or implement a download allowlist/warning.
- Keep the "Open File" action behind an explicit confirmation and validate the path is still the same file (inode/hash) before opening.

[H8] PPD performance-hold acquisition can leak duplicate holds and reorder release/acquire
File: hal/src/power_governor.cpp:150-186,249-272
Evidence:
- `setPerformanceHoldAsync(true)` checks `ppd_cookie_.has_value()` under the mutex, but the cookie is only stored after the asynchronous `holdPpdProfileSync()` returns.
- Two rapid `true` calls both see an empty cookie and both acquire a hold. The second completion overwrites `ppd_cookie_`; the first cookie is lost and never released.
- `shutdown()` releases only the single stored cookie.
- A release thread and a subsequent acquire thread are both detached, so the final PPD state depends on which D-Bus call completes last, not on the requested state.
Impact: The CPU can remain pinned in the performance profile after the UI says battery/zero-fan mode, or the requested hold can be lost. Repeated toggles can accumulate holds.
Recommendation:
- Serialize hold/release operations through one worker and a desired-state state machine.
- Track a set of outstanding cookies (or acquire only when no request is in flight).
- Join/cancel the worker in shutdown and release every cookie.
- Verify the final state after each transition if PPD exposes a property.

[H9] Local CEF installer reuses a world-writable /tmp path and downloads without integrity verification
Files:
- install-cef.sh:17-35
- update.sh:47-69
Evidence:
- If `/tmp/explorer-v2-poc/cef/Release` and `/tmp/explorer-v2-poc/cef/cmake/FindCEF.cmake` exist, `install-cef.sh` copies them into `~/.local/share/explorer-cef` and the build links against that `libcef.so`.
- `/tmp` is world-writable. On a multi-user machine, another user can create `/tmp/explorer-v2-poc/cef` with a malicious library and wait for the victim to run the installer.
- The normal download path uses `curl -fL` with no checksum or signature check.
- `update.sh` also downloads a CEF archive and extracts it with no checksum/signature verification.
Impact: Local privilege escalation to the installing user (code execution in the browser process) or a supply-chain compromise if the download host/CDN is compromised.
Recommendation:
- Remove the `/tmp` reuse path entirely, or require an explicit opt-in plus a checksum/signature.
- Pin SHA-256 checksums for the CEF archive and verify before extraction.
- Prefer a signed package/repository or a user-owned cache directory with 0700 permissions.
- Validate the extracted tree (libcef.so, chrome-sandbox, resources) before use.

[H10] Widevine is not actually registered with CEF
Files: engine/src/cef_flags.cpp:140-145; README.md:3,13; engine-builder/args.gn:20
Evidence:
- The code only appends the `enable-widevine` command-line switch when `/opt/google/chrome/WidevineCdm/manifest.json` exists.
- CEF requires the embedder to call `CefRegisterWidevineCdm()` with the CDM path and version; a command-line switch alone does not load a CDM.
- The hardcoded path only covers Google Chrome on some distributions; Fedora/Arch/Chromium paths are not checked.
- The README claims Netflix/Prime/Hotstar DRM parity.
Impact: DRM-protected streaming will fail even when a Widevine CDM is installed. The feature claim is misleading.
Recommendation:
- Call `CefRegisterWidevineCdm()` after CEF initialization (or before, per CEF version) with a discovered CDM path/version.
- Search common locations (`/opt/google/chrome/WidevineCdm`, `/usr/lib64/chromium/WidevineCdm`, `/usr/lib/chromium/WidevineCdm`, user data dirs).
- If no CDM is found, remove or qualify the DRM claim.

3. MEDIUM-SEVERITY FINDINGS

[M1] Adblock resource-type mapping misses media, fonts, objects, workers, and ping
Files: engine/src/cef_client.cpp:14-27; shield/include/explorer/shield/content_shield.hpp:15-23; shield/src/content_shield.cpp:96-107
Evidence:
- `ResourceKind` has only MainFrame, SubFrame, Script, Image, Stylesheet, XhrOrFetch, Other.
- `mapCefResourceType()` maps only those; RT_MEDIA, RT_FONT_RESOURCE, RT_OBJECT, RT_WORKER, RT_SHARED_WORKER, RT_PREFETCH, RT_FAVICON, RT_PLUGIN_RESOURCE all become Other.
- RT_PING and RT_CSP_REPORT are mapped to `xmlhttprequest`, so `$ping`/`$csp` rules do not match their real types.
Impact: EasyList/EasyPrivacy rules that use `$media`, `$font`, `$object`, `$worker`, `$ping`, or `$websocket` are less effective. Video ads and font/beacon trackers can slip through.
Recommendation:
- Extend ResourceKind and the mapping to the full CEF resource type set.
- Pass "ping", "media", "font", "object", "websocket", "worker", etc. to adblock-rust.
- Add tests with `$media`, `$font`, `$object`, and `$ping` rules.

[M2] "Secure origin" checks use prefix matching, not host equality
Files: app/src/browser_window.cpp:959-965; app/src/main.cpp:116-118
Evidence:
- `live_origin.rfind("http://localhost", 0) == 0` accepts `http://localhost.evil.com`.
- `live_origin.rfind("http://127.0.0.1", 0) == 0` accepts `http://127.0.0.1.evil.com`.
- The login-capture bridge uses the same prefix test on the frame URL.
- The exact `live_origin == req_origin` comparison limits the blast radius, but a credential saved for the attacker-controlled host can still be autofilled over plaintext HTTP, and the code labels the origin "secure" when it is not.
Recommendation:
- Parse the host and require exactly `localhost` or a loopback IP literal, or require `https://`.
- Do not use string prefixes for origin/security decisions.
- Reuse the same strict origin parser for vault save, vault fill, and login capture.

[M3] Vault key creation and persistence are not safe against concurrent instances
File: vault/src/password_vault.cpp:161-180,228-268
Evidence:
- `ensureKey()` generates a random key when the key file is missing, then `writeSecretFileAtomic0600()` unlinks the temp path and creates it with O_EXCL.
- If two processes start with the same profile and no key, both generate a key. The second write replaces the first key. The first process then encrypts `vault.enc` with a key that is no longer on disk.
- If `vault.key` exists but is short/corrupt, `ensureKey()` silently generates a new key and overwrites the old one, orphaning all existing credentials.
- `persistToDisk()` has no interprocess lock; two instances can overwrite each other's vault.enc (last writer wins).
- The file is fsynced, but the parent directory is not, so the rename may not survive a crash.
Impact: Credential loss or a vault that cannot be decrypted after two instances run concurrently or after key corruption.
Recommendation:
- Create the key with O_CREAT|O_EXCL and never unlink an existing key path.
- If the key exists but cannot be read/validated, fail closed and preserve it for recovery; do not silently rekey.
- Use a lock file/flock around key creation and vault writes.
- fsync the directory after rename; keep a backup of the previous vault.
- Consider a single-instance lock for the profile.

[M4] `--profile` does not isolate the vault or filter lists
Files: app/src/main.cpp:357-377,398-408
Evidence:
- Session and prefs use `cfg_.profile_dir`, but `services.vault` is constructed with `defaultProfileDir()` and the shield filters use `defaultProfileDir() / "filters"`.
- `--profile=/tmp/foo` therefore changes session/prefs/CEF cache but leaves credentials and filter state in the default profile.
- WebApp profiles under `profile_dir/webapps/<id>` still share the default vault and filters.
Impact: Profile isolation is incomplete; two profiles can share or overwrite credentials, and `--profile` does not provide the privacy boundary a user expects.
Recommendation:
- Pass `launch_cfg.profile_dir` to the vault and shield (or a dedicated `profile_dir/security` subdir).
- Decide explicitly whether webapps should share or isolate the vault; document it.

[M5] HUD updates rebuild all lists every two seconds and perform filesystem I/O on the UI thread
Files: app/src/browser_window.cpp:757-841,1458-1474; app/include/explorer/app/chrome_ui.hpp:715-841
Evidence:
- `onTelemetryTick()` runs every 2 s (5 s on battery) and calls `pushHudState()` when the HUD is open.
- `pushHudState()` serializes every credential, download, and installed webapp, then executes a large JS payload.
- `__updateHud()` clears `innerHTML` for the vault, download, and app lists and recreates every DOM node on each update (lines 746, 780, 811).
- `listInstalled()` scans `~/.local/share/applications` and reads each desktop file on the UI thread during every HUD update.
Impact: Focus and scroll position in the HUD lists are lost every 2 seconds; GC churn and disk I/O cause visible jank, especially with many credentials/downloads/apps.
Recommendation:
- Send only changed fields and update existing DOM nodes in place.
- Cache `listInstalled()` and invalidate on install/uninstall.
- Pause list refresh while the user is interacting with the HUD, or refresh only when the corresponding tab is opened.
- Move filesystem scans off the UI thread.

[M6] Download progress triggers full chrome and HUD state pushes
Files: engine/src/cef_client.cpp:301-329; app/src/browser_window.cpp:1218-1231
Evidence:
- `OnDownloadUpdated()` calls `observer_->onTabDownloadUpdated(rec)` on every progress update.
- `onTabDownloadUpdated()` calls `pushChromeState()` and, if the HUD is visible, `pushHudState()`.
- `pushChromeState()` rebuilds the full tab/vault/download JSON and executes JS; `pushHudState()` rebuilds all HUD lists.
Impact: Large downloads can cause many full UI updates per second, high CPU, and lost HUD focus. This compounds M5.
Recommendation:
- Throttle/coalesce download updates to ~4 Hz or on meaningful percentage changes.
- Update only the affected download row.
- Do not push the full chrome state for progress changes.

[M7] Background audio/video tabs are still throttled
Files: app/src/browser_window.cpp:1458-1474; policy/src/throttle_planner.cpp:14-37
Evidence:
- `reconcileRendererPriorities()` always passes an empty `media` set.
- `PidThrottlePlanner::reconcile()` throttles any tab not in `active_tabs` or `media_tabs` when on battery.
- There is no CEF audible-state integration, despite the planner's comment that it never throttles an audio tab.
Impact: Background music/video playback can stutter or be deprioritized on battery. Conversely, the planner's intended protection is not implemented.
Recommendation:
- Track audible tabs (CEF/Chromium audible state or a renderer-side hook) and feed them into `media_tabs`.
- If audible state is unavailable, be conservative and do not throttle background tabs that may be playing media.
- Add a policy test for shared PIDs and media tabs.

[M8] `PR_SET_TIMERSLACK` is per-thread, not process-wide
File: hal/src/power_governor.cpp:145-148; app/src/main.cpp:346-352; app/src/browser_window.cpp:1438-1450
Evidence:
- `applyTimerSlackNs()` calls `prctl(PR_SET_TIMERSLACK, ...)`, which affects only the calling thread.
- It is called on the main/UI thread and on the subprocess main thread, not on CEF's renderer, GPU, IO, or worker threads.
- The initial value (1 ns on turbo) and the later policy value (50 µs on AC) are inconsistent.
Impact: The power optimization is mostly ineffective, and the initial/later values differ without explanation.
Recommendation:
- Document that Linux timer slack is per-thread; apply it in each thread that should be affected (via a thread-start hook) or drop the claim.
- Align the initial and steady-state values.
- Measure the actual effect before keeping the tuning.

[M9] Refresh-rate control hardcodes 144 Hz, assumes eDP/GNOME, and races asynchronous applies
Files: policy/src/power_policy.cpp:37-39; hal/src/display_refresh.cpp:45-233,251-260
Evidence:
- `targetRefreshHz()` returns 60 on battery/cinema or 144 otherwise.
- `applyEdpRefreshSync()` only considers connectors starting with `eDP` and only talks to `org.gnome.Mutter.DisplayConfig`; KDE/Sway/X11 users get no effect.
- A 120 Hz panel on AC stays at 120 (best distance 24 > 20), a 165 Hz panel stays at 165 (distance 21 > 20), and a 144 Hz panel is the only one reliably switched.
- `setEdpRefreshRateAsync()` sets `last_hz_` before the apply completes; a failure is not retried, and rapid toggles spawn concurrent threads that can apply modes out of order.
Impact: The "60↔144 Hz" feature is machine-specific and can leave the display at an unintended rate after rapid AC/battery changes.
Recommendation:
- Discover the panel's supported modes and choose the highest rate ≤ a configured cap, or 60 on battery.
- Serialize applies through one worker; only update `last_hz_` after success; retry on failure.
- Support KDE/Sway or make the feature explicitly GNOME-only.
- Test with 120/144/165 Hz modes and rapid toggles.

[M10] GPU isolation fallback can select a discrete GPU; libva paths are Fedora-specific
Files: hal/src/gpu_isolator.cpp:35-58,60-85
Evidence:
- If no AMD/Intel render node is found, `discoverIgpuRenderNode()` falls back to `/dev/dri/renderD128` or the first node, which may be NVIDIA.
- `applyIsolationEnv()` only sets `LIBVA_DRIVER_NAME=radeonsi` when vendor == 0x1002; an NVIDIA fallback is not isolated.

Impact: Hardware decode can fail or the dGPU can remain powered on non-Fedora systems. The "Optimus D3cold" claim is not portable.
Recommendation:
- Return an empty/unknown node when no integrated GPU is found and let the caller decide.
- Detect the distro's libva driver directory or leave `LIBVA_DRIVERS_PATH` unset.

[M11] `isOnBatteryBoot()` treats a battery-less desktop with mains offline as battery-powered
File: hal/src/power_governor.cpp:121-143
Evidence:

[M12] Cookie preference is dead code; site-data clearing is incomplete

[M13] WebApp install can report success when nothing was written

[M15] Trusted chrome/HUD bridge is tied to browser ID, not URL or navigation state

[M17] Hand-rolled JSON parsing/escaping is incomplete

================================================================================
5. KEY DESIGN ISSUES
================================================================================

[D1] Async work has no ownership model
The code uses detached std::thread, raw `this`, `base::Unretained`, fork, and CefPostTask without a shared lifetime/cancellation abstraction. This is the root cause of H5/H6/H8. A small `TaskRunner`/executor owned by RuntimeServices, with `weak_ptr` tokens and join-on-shutdown, would remove a whole class of bugs.

[D2] The close state machine is implicit
`closing_`, `retiring_tabs_`, `open_browser_count_`, `DoClose`, `CanClose`, and `OnBeforeClose` interact without an explicit state enum or timeout. H3/H4 are symptoms. Model the window lifecycle as an explicit state machine (Open -> ClosingTabs -> ClosingWindow -> Destroyed) with cancellation and a timeout.

[D3] Test strategy is not trustworthy
The Release suite is vacuous (H1), tests are not hermetic (test_hal depends on the host GPU and `/bin/sleep`), and there are no integration tests for BrowserWindow/CEF, no Rust tests in CTest, and no sanitizer/fuzz jobs. A browser needs at least:
- Debug and Release test runs;
- ASan/UBSan/TSan CI;
- a headless CEF integration harness for tab lifecycle, session save/restore, downloads, and vault autofill;
- negative tests for every parser and origin check.

[D4] The security trust boundary is identified by browser ID, not by URL/context
H5/M15/M16 show the same pattern: a privileged capability is granted to a browser/view and then trusted for its lifetime. Prefer a capability token bound to the exact frame URL/context, with a navigation guard and a command allowlist.

[D5] Persistence is ad-hoc and duplicated
Session, prefs, vault, and webapp metadata each use their own hand-rolled format and error handling. A shared atomic-write + JSON/schema layer would fix M17/M23 and make migrations possible.

[D6] Hardware tuning is hardcoded to one machine
144 Hz, eDP/GNOME, Fedora libva paths, Ryzen 7 5800H V8 flags, `-march=native`, and AMD-only telemetry make the browser fragile on other hardware. The escape hatch (`EXPLORER_DISABLE_TUNING`) is useful, but the default path should degrade gracefully rather than assume Cezanne.

[D7] UI update strategy is "rebuild everything"
The HUD/chrome state pushes serialize and rebuild full lists on a timer and on every download progress event (M5/M6). A diff-based update model (or a small reactive store) would improve responsiveness and reduce IPC.

[D8] Error handling is not part of the design
Many operations can fail silently (M26). For a browser, install/update/save/clear operations need explicit user-visible outcomes and logs.

================================================================================
6. RECOMMENDED PRIORITY ORDER
================================================================================

1. Fix the test infrastructure (H1): Debug tests, always-on checks, no side effects in asserts, CI matrix.
2. Fix vault origin validation and key/persistence races (H2, M3), then add the missing origin/key tests.
3. Fix shutdown/session/close state (H3, H4): single session snapshot, explicit close state machine, reset on cancel, timeout for OnBeforeClose.
4. Fix async lifetimes and fork safety (H5, H6): executor + lifetime tokens; posix_spawn.
5. Fix download UX and Safe Browsing (H7).
6. Fix PPD hold serialization (H8) and refresh-rate worker (M9).
7. Fix installer/updater integrity and sandbox packaging (H9, M19).
8. Register Widevine or remove the claim (H10).
9. Address the medium security/functional items: M1, M2, M4, M12, M15, M16, M21.
10. Address performance/UI items: M5, M6, M7, M8.
11. Clean up low-severity items and align the README.

================================================================================
7. WHAT IS GOOD
================================================================================

- The module boundaries are clear and mostly enforced: HAL has no CEF/UI dependency, policy is pure, shield is behind an interface, vault is behind an interface, and webapp/engine/app are separated.
- The shield uses Brave's adblock-rust rather than a homemade matcher; the C ABI is small and the slice-based hot path avoids copies.
- The vault uses AES-256-GCM with a random 96-bit IV, a 128-bit tag, a 0600 key, atomic temp-file writes, and a tamper test.
- The webapp installer avoids shell invocation and validates app IDs/URLs against traversal/injection.
- The UI has a clear visual system and the documented 44 px bezel / 38 px tab bar / 1.05 zoom invariants are present in code.
- The privacy defaults (GPC/DNT, background networking disabled, no history, no sync) are sensible; the gaps are in coverage and validation, not intent.
- The Debug build exposed a real bug that the Release build hid; adding Debug CI is a high-leverage improvement.
